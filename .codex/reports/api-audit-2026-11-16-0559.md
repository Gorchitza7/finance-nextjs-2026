## 4. Проблемы на стороне сервера

### API Issue — коды валют в finance2 передаются в нижнем регистре

- Источник: finance2, `GET /api/finance2`.
- Фактические примеры: `"300 usd"`, `"200 eur"`.
- Ожидаемое значение: трёхбуквенные ISO-коды в едином верхнем регистре,
  например `USD` и `EUR`.
- Причина: формат источника допускает буквы без требования верхнего регистра;
  в одном ответе finance1 используются `USD`/`EUR`, а finance2 — `usd`/`eur`.
- Влияние: текущая версия приложения нормализует регистр, поэтому расчёт не
  ломается, но контракт источника неоднороден и усложняет интеграции.
- Критичность: **Warning**.
- Рекомендация: возвращать валютные коды в верхнем регистре и закрепить это
  требование в контракте API.

### Potential Issue — резервный API-ключ в коде приложения

- Источник: конфигурация запросов к finance1 и finance2.
- Фактическое значение: `process.env.FINANCE_API_KEY ?? "<замаскировано>"`.
- Ожидаемое значение: ключ обязателен и передаётся только через окружение.
- Причина: при отсутствии переменной приложение использует встроенное значение.
- Влияние: риск утечки и несанкционированного доступа; замечание относится к
  конфигурации приложения, а не к содержимому текущих API-ответов.
- Критичность: **Warning**.
- Рекомендация backend-разработчику: удалить fallback, сделать переменную
  обязательной и ротировать ключ, если встроенное значение уже публиковалось.

### Potential Issue — лишнее адресное поле в ответе finance1

- Источник: finance1, `GET /api/finance1`.
- Фактический пример: корневой объект кроме `transactions` содержит объект
  `address` с полями города, улицы и номера дома; значения замаскированы.
- Ожидаемое значение: минимальный ответ по контракту — объект с массивом
  `transactions`.
- Влияние: приложение поле не использует; лишние адресные данные увеличивают
  объём ответа и риск непреднамеренного раскрытия данных.
- Критичность: **Info**.
- Рекомендация: удалить поле из финансового endpoint либо явно описать его
  назначение, доступ и политику данных.

## 5. Проверки данных и влияние на приложение

### finance1

- Корневой объект содержит `transactions`: 8 записей.
- `paid`: 5 записей; `pending`: 1; `rejected`: 2.
- Фильтр приложения `type === "paid"` исключил 3 записи (`pending` и
  `rejected`). Это ожидаемое поведение текущего кода, а не подтверждённая
  ошибка API.
- Все использованные суммы — конечные положительные числа; нулевых,
  отрицательных, строковых или нечисловых значений нет.
- Валюты `USD` и `EUR` существуют и имеют курсы.

### finance2

- Корневой элемент — массив из 9 строк; все строки соответствуют формату
  `сумма код`.
- Все суммы положительные, с не более чем двумя знаками после разделителя;
  тысячных разделителей, научной нотации и символов валют нет.
- Валюты `usd`/`eur` после нормализации становятся `USD`/`EUR`; курсы есть.

### Курсы

- `result` равен `success`, `rates` — объект, `base_code` — `USD`,
  `rates.USD` — `1`.
- Коды курсов в верхнем регистре, значения положительные и конечные.
- Время обновления: `2026-11-16T00:02:31Z`; на момент аудита курс не был
  просрочен по указанному сервисом `time_next_update`.

### Воспроизведение расчёта

Сверка выполнена inline-скриптом по воспроизведённой логике
`app/lib/revenue.ts`, а не вызовом самого кода приложения.

- Сумма USD до конвертации: `3020.00 USD`.
- Сумма EUR до конвертации: `1910.00 EUR`.
- Курс EUR: `0.906623 EUR за 1 USD`.
- finance1 после фильтра: `1948.28 USD`.
- finance2: `3178.44 USD`.
- Ожидаемый итог приложения: **`5126.72 USD`**.
- Исключений, `NaN`, молчаливого обнуления и отсутствующих курсов на этих
  данных нет; успешных платежей в результате: 14.
- Точные дубликаты записей не обнаружены. Идентификаторы отсутствуют, поэтому
  для разных платежей с одинаковыми значениями окончательный вывод невозможен.
